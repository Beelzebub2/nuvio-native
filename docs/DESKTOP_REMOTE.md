# Control desktop playback from Android

1. Open Starlit on your desktop and Android phone. Sign in to the **same account on the same account server** on both devices. Guest accounts cannot use the remote.
2. Connect both devices to the same IPv4 Wi-Fi/Ethernet network. On Android open **Settings → PC controller**, which opens as its own full-screen page. This entry stays visible even when no PCs were detected. An automatic scan uses both UDP discovery and a bounded direct-IP search; tap **Search local network** under **Ways to connect** to retry, then select the desktop. Alternatively, use **Find Bluetooth PCs** with a compatible Windows desktop. The Settings search can also open the controller.
3. For the first connection, compare the six-digit code shown on both screens. Choose **Codes match on both devices** only when they agree. Reject unexpected requests or different codes. Later Bluetooth and Windows-PC Wi-Fi reconnections between the same approved devices do not require a code if their protected trust keys are still available.
4. Start a video on the desktop. The phone shows live playback state and controls for play/pause, seeking, volume/mute, subtitles, skipping the current intro/credits segment, and previous/next/selected episodes. Choosing an episode can require selecting its source in **Episode sources**, following the desktop's existing playback settings. **Find addon subtitles** loads available addon subtitles. P2P consent must still be confirmed on the desktop.

Once connected, the page splits into **Remote**, **Downloads** and **PCs** tabs. Closing the PC controller page keeps the session connected. Reopen it from Settings. Use **Disconnect** to end it; on desktop this is in the **Phone remote** window (**Settings → Account → Devices → Connect phone**). After disconnection, app restart, leaving the desktop player, or phone background/network interruptions, previously approved Bluetooth PCs can resume without another code using protected per-device trust keys. On Android, automatic Bluetooth reconnect is attempted only if the **most recently connected saved PC overall** used Bluetooth; if LAN was most recent, the controller searches the LAN instead. Saved PCs remain available for manual reconnection. Trusted Wi-Fi reconnects to Windows PCs do not require another code. macOS/Linux LAN sessions still need a code until native protected secret storage is available. Normal episode/source switches and account-token refreshes keep the connection. Signing out or changing account server stops discovery and disconnects the local session. Remote account sessions are revalidated at least once per minute; a server-revoked phone session is rejected on the next validation. Refreshed phone tokens are sent only inside the encrypted connection and are verified against the same account before any further command is accepted.

If no PC appears after searching, verify that both apps are signed into the **same non-guest account and account server**, the desktop app is open, and the phone and PC can reach each other on the local network. Press **Search local network** again after changing Wi-Fi or the PC's firewall settings; the button remains accessible even when already connected to another PC. A scan cannot proceed before account sign-in. iOS shows the controller entry with an unsupported notice, but scanning is currently available only on Android.

## Pair with a QR code

On desktop, open **Settings → Account → Devices → Connect phone**. Starlit opens a separate **Phone remote** window; the rest of the app stays usable while it is open. Once the local listener is ready, the window shows a QR code and its selected local IPv4 address. When a phone asks to pair, the window switches to the six-digit code check. If the PC has multiple network adapters, use **Choose network address** to select the address shared with your phone. After changing Wi-Fi or the PC’s IP address, close and reopen Phone remote to refresh both the QR code and manual-IP addresses. If the PC has no local network yet, connect it and reopen the window; no account restart is needed.

On Android, open **Settings → PC controller → Scan desktop QR code** inside Starlit. After a successful scan the controller checks that address and, once the PC answers, connects to it straight away and shows **Connecting to your PC** until the six-digit code check opens. A scanned code replaces any network search that is still running. Compare and approve the fresh codes on both devices. If the code names a PC on another network, the controller says so instead. The QR code contains only a versioned private IPv4 discovery hint, never credentials, account information or an approval. It does not open a website or run commands. The phone still probes the same subnet and verifies the account through the existing encrypted handshake.

Scanning uses the native Google Play services scanner without requesting camera permission in Starlit. Google Play services may need to download its scanner module on first use. If scanning is unavailable, canceled, or cannot read the code, use **Search local network** or enter the desktop's local IPv4 address manually.

## Safe desktop download management

After the encrypted session has been **approved on both devices** and the same Starlit HTTPS account has been verified, Android may view the status of up to 30 existing desktop downloads and pause/resume only tasks belonging to the desktop's **currently selected profile**. Open the same profile on the phone to receive the list. The desktop rechecks both the local profile and task state for each command.

The remote deliberately **does not** accept new download URLs, magnets, stream links, file paths, destination changes, cancellation, deletion, account settings, provider credentials, DRM workarounds or source selections. It cannot bypass content licensing or network protections. The phone receives bounded title/status/progress only; desktop paths, signed URLs, headers and credentials never enter this protocol payload. Every reconnection requires fresh account verification; Bluetooth and trusted Windows-PC LAN sessions use mutual device-key proofs instead of a new code confirmation. The desktop remains authoritative for the current queue, account and profile.

## Phone-to-PC playback handoff

With Android and desktop paired, tap **Play on Starlit PC** from an eligible movie/series details page, from a selected episode's poster actions, or from the Android player controls. For a series' main details action, the currently recommended episode is requested. The request carries only a bounded media identifier, content type, title, profile identifier and resume position, inside the already authenticated encrypted remote channel. The phone never sends playback URLs, torrents, files, headers, tokens or DRM material.

On the desktop, a separate prompt **Play on this PC?** names the requested title. The PC user must explicitly approve it. After approval, the existing Starlit desktop playback path opens its own source picker with the same account/profile checks, provider source restrictions and P2P consent flow it would use for a normal local play. Handoff does not auto-select a source or play media without approval. Both devices must use the same active profile; requests for stale or unrecognized IDs are rejected. Closing the pairing session, changing profiles or declining a prompt stops that request. This is an opt-in metadata handoff, not streaming from the phone or an unrestricted network receiver.

Allow Starlit through the desktop firewall on **private networks**. Discovery uses UDP **47788** and a stable encrypted-session TCP port **47789**; direct TCP discovery uses the same TCP port. On Windows, Starlit checks the inbound firewall rules in-app and can ask for a **one-time Windows administrator (UAC) prompt** to add rules for those two ports, limited to Private/Domain networks and the local subnet. Shortly after the PC starts listening, Starlit asks once if the firewall would hide it from phones (**Not now** is remembered), and the Phone remote window always shows the current firewall status with **Allow through firewall** and **Check again**. If the active connection is marked Public, use **Open network settings** to change a trusted home network to Private. No port forwarding is needed. Guest Wi-Fi/client isolation, VPN routing, and restricted corporate networks can prevent LAN discovery. Keep both apps foregrounded during pairing; account verification also needs internet access to the configured HTTPS account server. Multiple desktop processes on one computer can contend for discovery; use one running instance.

### Manual PC address, saved PCs and Wake-on-LAN (Android)

When broadcast discovery fails, open **Settings → PC controller → Enter address**. The desktop Phone remote window lists its local IPv4 addresses under **Other ways to connect**; enter one and tap **Find PC at this address**. The phone checks the fixed TCP port directly using a bounded nonce-bound account discovery probe, in addition to the older UDP discovery fallback. A **Search local network** scan checks up to 254 host addresses per private local interface using short timeouts and limited concurrency (at most two interfaces), so it works where broadcast fails but direct TCP is allowed. No cloud relay, arbitrary hostname, public IP, manual port or router forwarding is accepted. Compare and confirm a code on first pairing, after forgetting a PC, or if stored trust can no longer be verified.

After a successful two-sided pairing and HTTPS account verification, Android remembers that PC's sanitized name, local IP or Bluetooth MAC, connection type and last-seen time. **Previously paired PCs** can be reconnected or forgotten. Tapping a saved LAN entry checks its IP and then starts pairing without requiring another tap on a discovered device; previously approved LAN trust can skip the code confirmation on Windows PCs. The currently connected endpoint is labeled **Connected** and offers **Disconnect** instead of **Connect**. Forgetting the current PC disconnects it. These device-list entries are only discovery hints, not authorization. Bluetooth and LAN trust are stored separately as protected, account-scoped keys on both ends (Windows DPAPI and Android Keystore); the saved IP/name is never an approval. Forgetting the PC erases the phone's LAN trust credential. The desktop's random identity survives IP/Wi-Fi changes.

For compatible hardware only, configure **Wake-on-LAN settings** from a previously paired PC's ⋮ menu. Enter its Ethernet adapter's MAC manually and enable WoL in the desktop BIOS/UEFI, driver and operating system. **Wake PC** sends an opt-in magic packet through the active local interface to UDP port 9, with a repeat guard. This does not automatically wake any machine, reach the internet or authenticate the PC. The status reports that a packet was sent, **not** that the PC woke up. Sleep/hibernation behavior depends on hardware and router configuration.

LAN remote currently supports Android phones and the built-in desktop player on Windows, macOS, and Linux. Bluetooth remote currently supports Android to Windows using Bluetooth Classic (RFCOMM); iOS and other desktop Bluetooth hosts are not supported. External desktop players are not supported. Very large episode/subtitle/source lists are shortened to keep network messages bounded; the phone displays a notice when this occurs.

## Bluetooth remote (Android → Windows)

1. Enable Bluetooth on both devices and pair the phone with the Windows PC in the operating systems' Bluetooth settings. Windows may need its **Bluetooth & devices** settings open to be discoverable during initial OS pairing. Bluetooth Classic support on the desktop is required; BLE-only radios do not provide RFCOMM.
2. Open Starlit on the Windows PC, sign in, and check **Settings → Phone remote** for the Bluetooth availability message. An isolated native Windows RFCOMM service advertises the Starlit service ID while the desktop app is running.
3. On Android open **Settings → PC controller → Find Bluetooth PCs**, approve **Nearby devices** if prompted, and choose a PC found by the current Bluetooth inquiry. Previously OS-paired PCs are **not** presumed nearby: each new search clears the previous nearby results, and results expire after 60 seconds. Successfully paired Starlit PCs remain in the separate **Saved PCs** list for manual reconnect even if they are not discoverable. The search shows **Searching** while it runs (usually about 12 seconds, stopped after 30) and then either asks you to choose a PC or explains why none was found. Connection options are paused while a search or a connection is in progress, because a Bluetooth search interrupts a Bluetooth connection being opened. On Android 11 and below, Bluetooth discovery requires Location permission; Android 12+ requests only Nearby devices permissions.
4. Compare and confirm the six-digit code on **both** devices. The phone can then use the same playback controls and desktop download status controls, even without a shared Wi-Fi network. Both apps still need internet access for HTTPS account verification; Bluetooth does not bypass account authentication.

Bluetooth devices are never treated as trusted just because Android lists them as OS-bonded. Discovery names and MAC addresses are hints. The first Starlit connection requires the **same RSA/AES-GCM handshake, two-device code approval, account-token verification and command allowlist** as LAN. After approval, an independent random shared trust key is stored encrypted under Android Keystore and Windows user DPAPI. Subsequent Bluetooth connections exchange mutual HMAC proofs bound to a new encrypted handshake; only successful proof from both sides skips the two code dialogs, **never HTTPS account verification**. Missing, corrupted or forgotten keys fall back to first-time approval. **Forget** removes Android's protected key and saved PC entry. Signing out or clearing local account data also removes keys on Android. A Windows helper forwards RFCOMM bytes solely to a loopback-only TCP listener; it cannot connect to arbitrary network destinations or directly dispatch playback commands. No Bluetooth content streaming is implemented; this feature transports control commands only.

Bluetooth connections try authenticated RFCOMM first. If the PC is already paired at the OS level but its older adapter cannot establish the secure link, Android retries the same Starlit service UUID using legacy-compatible RFCOMM. On pre-Bluetooth 2.1 adapters that lower-level link may not be encrypted; Starlit's own encrypted session and mandatory mutual approval or stored trust proof plus HTTPS account verification still protect every command and credential. If both modes fail, confirm **Bluetooth available** in the Windows Starlit Phone remote window. Bluetooth LE-only radios and older proprietary Windows Bluetooth stacks without RFCOMM host support cannot use this transport; choose the existing Wi-Fi/QR controller instead.

## Protocol and trust boundary

Discovery is an untrusted hint: it includes a request nonce, a nonce-bound account/server filter, and a device label, and accepts only IPv4 addresses on an active private interface's actual subnet. A desktop responds only to discovery for its current account/server. The desktop applies the same subnet restriction to accepted TCP connections. Discovery labels and filters are never authentication or a trust decision.

Each connection uses a new 2048-bit RSA key and two fresh 32-byte contributions (with a five-byte backwards-compatible capability marker when using the new Bluetooth reconnection protocol). The desktop sends its public key and SHA-256 commitment to its hidden random nonce. The phone then fixes its contribution by encrypting a fresh session secret with RSA-OAEP (explicit SHA-256 and MGF1-SHA-256). Only after receiving that ciphertext does the desktop reveal its committed nonce. Both peers verify the commitment and derive the displayed code and directional AES-256-GCM keys from the complete transcript, including the secret. Committing before the phone contribution prevents adapting the desktop nonce to grind a matching code after learning that contribution. Both screens require explicit human confirmation for first-time pairing or after trusted Bluetooth reconnection cannot be verified; no credentials or commands are exchanged over the unauthenticated discovery channel.

After first-time confirmation (or successful Bluetooth trust proof), the desktop verifies its own session against its configured HTTPS `/auth/v1/user` endpoint, then sends its account/server identity inside the encrypted channel. The phone checks that identity before sending its access token inside the channel. The desktop verifies the phone token against its own configured HTTPS endpoint and requires the same account ID. Redirects are disabled, and neither an advertised address nor a phone-supplied server can select the verification endpoint. Refresh tokens are never shared. Ephemeral session keys and received access tokens remain in memory and are not logged or persisted; only independently generated Bluetooth reconnect credentials are persisted using platform-protected storage.

Encrypted frames use distinct keys for each direction, monotonic counters as GCM nonces, protocol-bound authenticated data, and strict replay/order checks. Framing, verification responses, and playback menus are size-bounded. Only an explicit command allowlist reaches the active desktop player; stale playback generations, unknown choices, and invalid values are rejected. Remote actions reuse the desktop's existing episode, source, subtitle, skip, and watch-progress behavior.

Primitive/platform references: [Java Cipher](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/javax/crypto/Cipher.html), [Android cryptography guidance](https://developer.android.com/privacy-and-security/cryptography), [Android local network access](https://developer.android.com/privacy-and-security/local-network-permission). The current Android target is 36, so the existing INTERNET permission covers this LAN traffic; apps targeting 37 will need the platform's runtime local-network permission workflow. LAN TCP is encrypted directly and does not loosen Android's HTTP cleartext policy.
